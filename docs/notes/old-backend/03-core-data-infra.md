## 1. ES Express and Express.Core

### 1.1 Short answer

There are **two different things called "Express"** in this repo. Do not mix them up.

| | **A. "ES Express" product** | **B. "Express module" inside YES** |
|---|---|---|
| What it is | A separate self-storage product line: unmanned / self-service units with Noke smart locks, its own facilities, units, storage plans, insurance plans, promo codes, rentals, charges, refunds, move-outs. **No SiteLink.** It is its own property-management system. | A small "book an Express unit" flow added to the YES mobile app (2024-06, commit `e9b8e3d3 feat:express integration`). Reserve a unit, save a card, pay with Stripe. **No SiteLink.** |
| Database | **Its own MySQL 8 database** on a separate RDS cluster endpoint (config key `Express:ConnectionString`). | The **main YES database** (tables `ex_*`). |
| Code in this repo | `ExtraSpaceCMS/Express.Core/` (class library: entities, repositories, services) + the CMS area `ExtraSpaceCMS/admin_cms/Areas/express/` (14 controllers, routes `/express/...`). | `ExtraSpaceAPI/mobile_api/Controllers/ExpressController.cs` (`/v1/Express/...`), `BL/ExpressBL.cs`, `DAL/ExpressDAL.cs`; CMS screens in `admin_cms/Controllers/ExpressModule/` (Express Import, Ex Storage Plan, Ex Unit Discount Plan, Ex Unit Sizes, Ex Unit Types, Ex Reservation, Ex Audit Log). |
| Customer-facing app/backend | **Not in this repo (inferred).** The Express DB has tables that only a customer backend writes: `user_jwt_tokens`, `otps` (login / forgot password / move-out), `temp_guest_users`, `guest_login_fails`, `users.fcm_token`, `users.jumio_account_id`, `registration_type` = jumio / myinfo. A grep shows **no code here writes** `UserJwtTokens`, `Otps`, `TempGuestUsers` or `GuestLoginFails`. Recurring rent charges are also not generated by any job here. So a separate ES Express API + app exists somewhere else. | The YES mobile app (same app as the rest of `/v1/*`). |
| Admin | Same CMS image, `express` area. Admin users are the main-DB `cms_user` rows; per-user Express facility rights in main-DB `cms_user_express_facilities`. | Same CMS, normal menus 19–23 (`admin_cms/Common/EnumCollection.cs` `Menu`). |

### 1.2 What `es_express/` and `ExpressCms.Dockerfile` build

- `ExtraSpaceCMS/es_express/ExpressCms.Dockerfile` is **byte-identical** to `ExtraSpaceCMS/ExpressCms.Dockerfile`, and both are the same as `ExtraSpaceCMS/admin_cms/Dockerfile` (only a trailing newline differs). The folder `es_express/` holds nothing else.
- All three build **`admin_cms.csproj`** (which has a `ProjectReference` to `Express.Core`, `admin_cms/admin_cms.csproj:253`). There is no separate Express app.
- `.github/workflows/staging-esexpress-manual-deploy.yml` builds `ExtraSpaceCMS/ExpressCms.Dockerfile` → ECR repo `esexpress.cms.staging` → ECS service `esexpress_cms_staging` on cluster `staging-es-cluster`. So "ES Express staging CMS" is **the same CMS image deployed as a second ECS service** (inferred: used to test the Express area before merging to the normal staging CMS; branches `dev/es-express-*`, `yes-staging-for-express*`).
- **Production CMS also builds from `ExpressCms.Dockerfile`** (`.github/workflows/production-cms-manual-deploy.yml`), so the production CMS contains the Express area. There is no production-only Express workflow.

Total distinct objects seen: about **160 tables + 1 view**, plus stored procedures (section 2.6).

How the contexts relate:
- `mobile_api/Entities/Context.cs` (97 DbSets) and `admin_cms/Entities/Context.cs` (107 DbSets) map the **same main DB**. The CMS has 10 extra tables (`ex_audit_log` + 9 SiteLink dashboard tables). Small column drift: `ex_user.UEN` + `is_corporate` and `reward.is_open_value` only in the API model; `cms_user_express_facilities.es_user_address_editable` and `ex_unit_storage_plan.parent_unit_type_id` only in the CMS model.
- `Express.Core/Entities/Context.cs` maps the Express DB. Two names collide with the main DB but are **different tables in a different DB**: `otps`, `payment_methods`.
- Charset: main DB is `utf8` (3-byte) with mixed `utf8_general_ci` / `utf8_unicode_ci`; `Noke_*`, `otps`, `push_notification` have some `latin1_swedish_ci` columns. Emoji will not store in the main DB. Express DB is `utf8mb4`.
- No EF concurrency tokens anywhere. Express `units.row_version` is a plain bigint set by app code (`Utils.RowVerion()`).

### 2.5 Conventions: money, time, soft delete, audit

**Money**
- Main DB: `decimal(18,2)` mapped to C# `decimal` (not `double`). SiteLink report copies `decimal(30,4)`. **`sitelink_receipt.dc_amt/dc_bal/dc_pmt_sum` are `decimal(10,0)`** — cents are lost there. Points are `int` (`user.points`, `point_transaction.total_points`, `reward.exchange_point`); earned points are rounded **up** (`Math.Ceiling`, `mobile_api/DAL/PaymentDAL.cs:1104`). `redeem_reward.discount_value` is `int`.
- Express DB: `decimal(18,2)` mostly; `charges.amount/tax` `decimal(13,4)`; `promo_codes.discount_amount` `int`. Rounding helper `ToTwoPlaceDecimal` = `Math.Round(x, 2, MidpointRounding.ToPositiveInfinity)` (`Express.Core/Utils.cs:54-57`).
- Currency is per deployment (`Country:StripeCurrency` sgd / myr; `Country:Currency` S$ / RM). Express has a `currencies` table.

**Time**
- All business timestamps are `datetime(3)` with **no zone info**. Containers run with `ENV TZ=Asia/Singapore` (all Dockerfiles), so `DateTime.Now` = Singapore time.
- Mixed writers: `created_on` is set with `DateTime.UtcNow` in most places (API 34 vs `Now` 1; CMS 32 vs 9; Express.Core 80 vs 2 — counts of `CreatedOn/DtCreated = DateTime.*`). Overall `DateTime.Now` appears 45× (API), 181× (CMS), 54× (Express.Core). So a column can hold UTC in one row path and SGT in another — **treat as mixed; verify per column before migrating.**
- SiteLink dates are parsed then `.ToUniversalTime()` (`mobile_api/Services/SiteLink/SiteLinkAPIs.cs:1085-1119`).
- SiteLink dashboard tables use MySQL `timestamp` with `CURRENT_TIMESTAMP` default.
- log4net: payment/debug/tenant logs use `RawTimeStampLayout` (local SGT); `cms_audit_log` uses `RawUtcTimeStampLayout` (UTC).
- Hangfire recurring jobs mostly use `TimeZoneInfo.Local` (= SGT in the container); `RecurringPaymentJob` uses `Asia/Singapore` explicitly (`admin_cms/Controllers/RecurringJobController.cs:224`).
- CMS JSON writes every `DateTime` with a `Z` suffix regardless of Kind (`admin_cms/Common/DateTimeConverter.cs`). CMS culture `en-US` with short date `dd/MM/yyyy`.

**Soft delete** — no global flag.
- Main: `user.status = 3 (Deleted)`; `status` bool/smallint "active" flags on most content tables; `payment_methods.is_deleted bit(1)`.
- Express: `users.status = 'deleted'`; facilities/plans/types/sizes `status` active/inactive; units `inactive`/`donotrent`; rentals `inactive`/`superseded`.

**Audit columns**
- Main: `created_on`, `updated_on` (+ `created_by`, `updated_by` on content and CMS tables). Admin actions → `cms_audit_log`.
- Express: `dt_created`, `dt_updated` (some `created_at`/`updated_at`); admin actions copy `cms_user_id` + `cms_user_name` into the row, and → `cms_audit_trails`.

**Ids** — main: GUID strings `varchar(36)`; some int ids (`master_facility.id` = SiteLink SiteID, `cms_menu.id`); auto numbers `user.membership_no`, `payment.payment_no`, `*.seq_no`/`seq_id`. Express: prefixed GUID strings; `receipt_number` int + `receipt_uid`.

### 2.6 How schema changes were applied

- **Database-first, by hand.** EF code-first migrations existed only in May–June 2020 (`mobile_api/Migrations/20200527185926_Init.cs`, `..._AddSaltColumn.cs`) and were deleted on 2020-06-04. Since then the contexts are re-scaffolded from the live DB (`#warning To protect potentially sensitive information...` scaffold header in `mobile_api/Entities/Context.cs` and `Express.Core/Entities/Context.cs`). No `Database.Migrate()` / `EnsureCreated()` in code.
- `ExtraSpaceCMS/update-database-scripts/cms/report/240502/` holds the only SQL in the repo: 6 stored procedures for **Express DB reports** (`sp_CustomerReport`, `sp_UnitReport`, `sp_RentalInfo`, `sp_GetRentalsByFacilities`, `sp_GetChargesByFacilities`, `sp_GetDonotrentRecordsByFacilities`), committed 2024-02-05. Each script is `DROP PROCEDURE` + `CREATE PROCEDURE`. **They do not match what runs in production:** every script declares only `IN _unitId` but the body uses `_facilities`, `_start`, `_end`, `_user_id`, `_unit_id`. So the real definitions live only in the database.
- Other stored procedures called by code but **not in the repo**: `sp_ErrorLog` (log4net), `sp_CheckToken`, `sp_GetPagingData2`, `sp_DashboardStatus_V2`, `sp_StorerReport`, `sp_RewardReport`, `sp_PointExpiry`, `sp_VoucherExpiry`, `sp_LastRentalInfo`. 🔴 **Committed secrets (live production values)** in:

- `ExtraSpaceCMS/admin_cms/appsettings.json`, `.Development.json`, `.Staging.json`, `.Production.json`

- `ExtraSpaceCMS/admin_cms/express.firebase.production.json`, `express.firebase.staging.json` (Google service-account **private keys**)
- `ExtraSpaceAPI/mobile_api/Entities/Context.cs` and `ExtraSpaceCMS/Express.Core/Entities/Context.cs` (`OnConfiguring` DB connection strings with passwords)
- `ExtraSpaceAPI/mobile_api/log4net.config`, `ExtraSpaceCMS/admin_cms/log4net.config` (DB connection strings)
- `ExtraSpaceCMS/admin_cms/wwwroot/secure/keys/key-*.xml` (ASP.NET Data Protection keys; inside `wwwroot`, so possibly downloadable via static files — **verify**)
- Same pattern on `mys-yes-production`.
Kinds of secrets present (by pattern check): Stripe **live** secret keys, AWS access key ids + secrets, SendGrid API key, MySQL passwords, SiteLink corporate password, Noke API keys, JWT signing key, AES key/salt/IV, SMSGlobal, WOGI and UniqueGift credentials, FCM server key, BasicAuth password.

🔴 **Secrets printed into CI logs**: `ExtraSpaceAPI/mobile_api/Dockerfile-GithubAction` (used by the SG and MY production and staging API workflows) runs `RUN cat appsettings.json`, so every API build log shows the full config. `admin_cms/Dockerfile-GithubAction` has the same line but no current workflow uses it.

🔴 **Same keys across environments and countries**: AES key identical in staging and production and in SG and MY; JWT signing key identical in SG and MY production. Anyone with staging config can decrypt production encrypted columns.

🔴 **Per-site Stripe secret keys stored in the DB** (`master_facility.stripe_secret_key`, `ex_facility.stripe_secret_key`), AES-encrypted with the committed key → effectively readable by anyone with the repo and a DB copy.

🔴 **Stripe webhook not verified**: `mobile_api/Controllers/WebhookController.cs:44-46` calls `EventUtility.ParseEvent(json)` without a secret; the `Stripe-Signature` header is read but never checked. No webhook-secret config key exists.

🔴 **Card data**: no PAN/CVV column exists in any DB (checked all entities). Stored: Stripe customer ids, PaymentMethod ids (main: AES-encrypted), brand, last 4, expiry. But the API calls SiteLink **`SimplePaymentWithSource`** with a **hard-coded public test card number per brand** (`mobile_api/DAL/PaymentDAL.cs:812-833` and `2641-2664`) to post Stripe-paid amounts into SiteLink. Not real card data, but it is a card-carrying SiteLink operation, which the new spec forbids.

🟠 Personal data: Express `users.nric_fin`, `temp_guest_users.nric`, `date_of_birth` stored in plain text (masked only on display, `MemberRepository.cs:294`).
🟠 Express CMS-created members get an initial password = birth date `yyyyMMdd` + last 4 of NRIC, or postal code + last 4 of UEN (`Express.Core/Utils.cs:171-186`, used in `MemberRepository.cs:1576, 2148`). Guessable.

Main app uses the closed `Codigo.Crypto.dll` with the same member names (inferred same algorithm). Field AES uses `PasswordDeriveBytes` (PBKDF1, 2 iterations), CBC.
🟠 DB and Redis connections without TLS (`SslMode=none`, `ssl=False`).
🟠 API CORS allows **any origin with credentials** (`mobile_api/Startup.cs:92-101`); Swagger UI public in production.
🟡 Images (rewards, facilities, plans, unit types/sizes, regions) are uploaded as public-read; Express rental documents in `rentals/` are uploaded **private** (`makePublic: false`, `Express.Core/Repository/MemberRepository.cs:2034`).
🟠 SMS text and phone number written to stdout logs (`mobile_api/Services/SMSGlobalService.cs:34-40`; the text carries the OTP when the SMS is an OTP — inferred); `mobile_api/Services/AWSSMSService.cs` logs the PIN explicitly. `api_logs.NokeRequestHeaders` may contain the Noke API key (inferred from the column name and branch `yes-production-nokelogheader`).
🟡 Stored procedures and log inserts built by string concatenation (`MobileApiLoggerDAL`), escaped but fragile.

## 8. Data migration notes

What a new system must carry over, per DB. "Re-create" = do not copy, set up fresh.

**Main YES DB (per country: SG, MY)**
- **Customers**: `user` (identity, contact, `membership_no`, `membership_date` — tier depends on it, `status`, password hash + salt), `user_tenantsite` (link to SiteLink tenant per site — critical for billing), `user_storage_unit`, `user_device` (push tokens), `user_notification` (history, optional).
- **Points**: `user.points` is a cached balance; the truth is `point_transaction` (earned/used/adjusted, `point_use`, `expiry_on`, `status`). Migrate the ledger and recompute/compare the balance.
- **Vouchers / rewards**: `redeem_reward` (issued vouchers incl. UniqGift voucher id / short URL / auth code, expiry, status), `reward`, `reward_category`, `reward_image`, `key_value` (`award_points_category`, `common password`).
- **Saved payment / Stripe**: `user_payment_card.stripe_customer_id`, `default_card`, `recurring_card` (decrypt with the old AES key during migration), `is_recurring`. Stripe accounts are per site (`master_facility.stripe_*`): the new system needs the list of Stripe accounts and which site uses which; re-enter keys, do not copy.
- **Payment history**: `payment`, `payment_facility`, `payment_unit`, `payment_charge`, `payment_transaction`, `user_payment`, `request_refund`, `sitelink_receipt` (note `decimal(10,0)` amounts). Needed for history screens, refunds and reconciliation with Stripe and SiteLink.
- **Reservations / rentals**: YES has **no reservation table** — rentals, reservations and invoices live in SiteLink. Only the Express module keeps them (`ex_rental`, `ex_payment_transaction`, `ex_user`, `ex_user_payment_card` with Stripe customer ids).
- **Sites and locks**: `master_facility` (SiteLink site ids, location codes, Noke site id), `Noke_Unit` mapping, active `Noke_Shares`.
- **Content**: `contents`, `faq`, `faq_item`, `post`, `post_tag`, `tag`, `post_view` (optional), `contact`, `push_notification` (+ facility), `app_version`, `feedback`, `feedback_subject`.
- **Admin**: `cms_user`, `cms_role`, `cms_menu`, `cms_menu_permission`, `cms_user_facility`, `cms_user_express_facilities`, `cms_audit_log` (archive). Consider forcing admin password resets.
- **Do not migrate**: `hangfire_*`, `api_hangfire_*`, `user_token`, `user_pin`, `forgot_password`, `otps`, `verify_facility_pin`, `Noke_Pin_Failed`, `cms_user_devices`, Redis. Optional archive: log tables, `api_logs`, SiteLink dashboard snapshot tables (they can be rebuilt from SiteLink).

**ES Express DB (only if ES Express moves to the new platform)**
- Customers `users` (+ `companies`, `addresses`; NRIC, DOB — PDPA review first), `payment_methods` (Stripe PM tokens), `users.stripe_customer_id`, Stripe Connect `facilities.stripe_account_id`.
- Contracts and money: `rentals` (with JSON plan snapshots and signed-document S3 URLs), `charges`, `transactions`, `charges_transactions`, `refund_transactions`, `move_out_*`, `promo_code_usage_records`. This is a full billing ledger — outstanding `charges` are money owed.

- Ops: `unit_lock_shares`, `unit_donotrent_records`, `battery_records`, `unit_viewings`, `user_ban_records`, `user_remarks`, `terms_conditions`, `privacy_policies` (keep versions), `cms_audit_trails`, `notifications`.

**Cross-cutting migration rules**
- Passwords: keep PBKDF2-SHA1 (1 000 iterations, separate base64 salt/hash) verification for old hashes and re-hash on next login, or force reset. The main app's exact algorithm is inside `Codigo.Crypto.dll` — confirm before relying on it.
- Encrypted columns (`user_payment_card.default_card/recurring_card`, `master_facility.stripe_secret_key`, `ex_facility.stripe_secret_key`, others via `IAESEncryption`) must be decrypted with the old AES settings during migration.
- Dates: check each `datetime(3)` column for UTC vs SGT before converting to UTC.
- Money: main DB is `decimal`; the new spec uses `double precision` — check rounding on every converted column.
- Ids: main GUID strings, Express prefixed GUIDs, many int SiteLink ids. Keep old ids in a mapping column for reconciliation.
- S3 objects: either keep the buckets or copy objects and rewrite stored URLs.
- Get a full `mysqldump --no-data --routines` of main, log and Express DBs; the repo does not hold the real stored procedures.
